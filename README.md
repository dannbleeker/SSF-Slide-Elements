# SSF Slide Elements

A library of ready-made slide elements for PowerPoint, as an Office.js task pane
add-in. Browse the collection, click one, and it lands on the slide you are on —
with every font, colour, gradient, table and chart exactly as it was drawn.

Part of the SSF add-in family, alongside [SSF Merge](https://github.com/dannbleeker/ssf-merge)
(mail merge for PowerPoint) and [SSF Charts](https://github.com/dannbleeker/ssf-charts)
(native, editable charts).

## What it does

The shipped library is **98 elements in 10 sections**, harvested from a
PowerPoint deck that is the authoring surface:

| Section | Elements |
| --- | --- |
| Hvide kasser | 34 |
| Hvide kasser med sorte overskrifter | 4 |
| Kun streger | 11 |
| Procesflow | 18 |
| Tabeller | 6 |
| Trekanter | 4 |
| Dokumentstruktur | 5 |
| Grå kasser | 9 |
| Markeringer, stempler m.m. | 3 |
| One-page templates | 4 |

You browse by slide; what gets inserted is the **content** of that slide, not
the slide. The title and the slide number stay behind — they name and number the
library, they are not part of the element.

## Adding an element

Open the library deck, draw the thing, save, push. That is the whole procedure.

There is no sidecar file to keep in sync and no naming convention to remember,
because the deck already says everything the add-in needs:

- **The layout says what a slide is for.** A slide on the `Sektionsadskillelse`
  layout opens a section; a slide on `Kun titel` is an element; `Frontpage` is
  the cover and is skipped.
- **The title placeholder is the name** — of the section on a divider, of the
  element on a content slide.
- **A placeholder is furniture and everything else is the element.**

Then regenerate the catalogue and commit it:

```bash
npm run build:lib && node scripts/harvest.mjs
```

CI fails a pull request where the deck and the committed catalogue disagree.

## How it works

A .pptx is a zip of XML parts, and the insert happens **in the file**.

Office.js has no call that puts arbitrary markup onto a slide:
`setSelectedDataAsync` will not take OOXML in PowerPoint, and the shape
collection can only add geometry it has a method for — so an element with a
gradient, a table or an icon cannot be reproduced through the API without losing
something. So the add-in reads the open presentation, splices the element's
markup into the shape tree of the slide you are on, reduces the package to that
one slide, hands it back through `insertSlidesFromBase64`, and removes the slide
it replaced.

Source and destination are the **same deck**, which is what makes this safe: the
spliced slide carries the deck's own layout, master and theme, so an element
adopts your brand exactly as it would if you had pasted it. There is no theme to
reconcile and no drift to correct.

Four things are rewritten on the way in, each with a failure that opens as
"PowerPoint found a problem with this file": part names, nested relationship
targets, relationship ids, and shape ids. `src/core/element/verify.ts` checks all
four, and the suite runs it over every one of the 98 elements on every commit.

## Layout

| directory | what it owns |
| --- | --- |
| `src/core/pptx/` | the package: the zip, its parts, relationships, content types |
| `src/core/catalogue/` | the harvest — a library deck in, a catalogue out |
| `src/core/element/` | `splice.ts` (the insert) and `verify.ts` (is it still a valid slide) |
| `src/core/preview/` | the thumbnail, drawn from the element's own geometry |
| `src/host/` | the DECISIONS about talking to a host, all pure and all tested |
| `src/office/` | the Office.js CALLS, and nothing else |
| `src/pane/` | `render.ts` (the picker's DOM) and `main.ts` (the only file here that touches Office.js) |
| `template/` | the library deck. The authoring surface |
| `public/catalogue/` | generated by the harvest, committed, shipped |

`src/core` has zero Office imports and `src/office` makes no decisions of its
own; `test/architecture.test.ts` holds both directions.

## Commands

```bash
npm run dev            # the pane at localhost:3000
npm test               # the whole suite, including the 98-element splice sweep
npm run typecheck
npm run lint
npm run build:lib && node scripts/harvest.mjs    # regenerate the catalogue
npm run build          # the site, for GitHub Pages
npm run pane-shots     # render and measure the pane at 320 and 512, both themes
```

Every npm script is FLAT. A script that nests `npm run` is blocked by AppLocker
on the owner's Windows box, which is where this gets run.

## Installing it

The add-in is served from `ssf-elements.struktureretsundfornuft.dk`. Sideload
`manifest-prod.xml`; `manifest.xml` points at `localhost:3000` for development
and needs a certificate (`npx office-addin-dev-certs install`).

The floor is PowerPointApi 1.2, checked at runtime rather than declared — a
declared requirement the host lacks makes an add-in vanish from the ribbon with
no diagnostic at all.

## Status

The file engine is proven: 98 of 98 elements splice into a real deck and verify
clean, in the suite, on every commit. **The host handshake is not yet proven
against a real PowerPoint** — see `docs/UNPROVEN.md` for exactly what is
measured and what is assumed.
